### AUTH-04: セッショントークンとデバイスシークレットの有効期間

`06-auth.md` §3 では以下を暫定値としている。

- `sessionToken`: 12時間。端末は5〜15分間隔でアップロードするため、再取得は1日2回程度。
  短くすればトークン露出の窓が狭まるが `/device/token` の呼び出しが増える
- `deviceSecret`: 無期限(再ペアリングまで)。定期的なローテーションを入れるかは未定。
  入れる場合はアップロードのレスポンスに新しい secret を同梱する Pull 型が候補
- Cognito Web Pool 側のトークン有効期間(Access / ID / Refresh)も既定のままでよいか未確認

### AUTH-05: ペアリング開始のレート制限値

`POST /devices` は DynamoDB への書き込みのみになり、Cognito ユーザー作成もメール送信も
伴わなくなったため、コスト面の切迫度は下がった。それでも無制限に発行できると
QR の総当たり試行の母数が増えるため上限は設ける。

暫定案: 10件/時。あわせて1オーナーが保持できる端末数の上限も決める。
Device レコードをペアリング開始時点で先に作る設計(`06-auth.md` §2)にしたため、
「端末を追加」を連打すると `PENDING` の行が溜まる。上限はこの観点からも要る。

### AUTH-07: Google OAuth クライアントの本番設定

要求スコープが `openid` `email` `profile` のみで機微スコープを含まないため、Google の審査(verification)は
不要と見込んでいるが未確認。あわせて OAuth 同意画面のブランド設定(アプリ名・ロゴ・
プライバシーポリシーURL・利用規約URL)が必要になる。ポートフォリオ用途でこれらのページを
どこまで用意するか。

**Web ログインを Google SSO のみとしたため、緊急度を「高」に引き上げた。** 代替のログイン手段が
存在しないので、ここが通らないと誰もログインできない。なお `profile` スコープは
サイドバーのアバター画像(`03-web.md` §2)に必要。

### AUTH-08: Web 側ログアウト時のトークン失効方針

ブラウザのトークンを破棄するだけにするか、Cognito の `GlobalSignOut` まで呼んで
Refresh Token を失効させるか。

### AUTH-09: 「応答なし」と判定する閾値

`03-web.md` §3 の状態モデル(`PENDING` / `ACTIVE` / `REVOKED`)により、
「Web から切断された端末」と「単に圏外・電源断の端末」は `status` で区別できるようになった。
残るのは、`ACTIVE` のうち何秒受信がなければ「応答なし」と表示するかという閾値のみ。

暫定値は **送信間隔の3倍**(5分設定なら15分)。1回の送信失敗では応答なしにせず、
連続して落ちたときに初めて表示を変える意図。

### AUTH-10: 端末のオーナー移管・共有の可否

現状は「1端末 = 1オーナー」「オーナーは複数端末を持てる」前提。
端末を別アカウントに移す、または複数アカウントで閲覧を共有する機能をスコープに入れるか。
MVP 外とする可能性が高いが、DynamoDB のキー設計が後から効いてくるため、
DB 設計(DATA-01)を確定する前に方針だけ決めておきたい。

### AUTH-11: 監査ログの取得範囲

「誰がいつ端末を追加/削除したか」「ペアリングが何回失敗したか」を記録するか。
記録する場合の保存先(DynamoDB か CloudWatch Logs か)と保持期間。

### DATA-01: DynamoDB シングルテーブルの PK/SK・GSI 設計

シングルテーブル設計を採る方針は決定済み。実際のキー設計は未着手。
少なくとも以下のアクセスパターンを満たす必要がある。

- オーナーの全端末を一覧する(ダッシュボードの最新スナップショット一覧)
- 特定端末の観測履歴を新しい順に取得する(タイムライン表示)
- Lambda Authorizer が端末の存在・`status`・`sessionTokenHash`・`sessionExpiresAt` を
  1回の GetItem で確認する(`06-auth.md` §3)
- ペアリングセッションを `pairingCode` で引き、条件付き Update で1度だけ消費する(TTL 属性つき)
- ペアリング成功時に、上記の Update と Device レコードの Put を `TransactWriteItems` で1コールにまとめる

AUTH-10(オーナー移管・共有)の方針がキー設計に影響するため、先に AUTH-10 を決める。

### APP-01: 送信間隔の初期値

5分・10分・15分から選択可能とする方針は決定済み。初期値が未決(`00-overview.md` §6)。

### APP-02: オフラインバッファの上限

端末側で一定件数/容量上限つきのローカル保持を行い、上限超過分は古いものから削除する方針は決定済み。
具体的な上限値が未決。送信間隔と保持したい時間(何時間の停電・圏外まで耐えるか)から逆算する。

### APP-03: 画像の保持期間・解像度・フォーマット

S3 ライフサイクルによる自動削除の期間は `00-overview.md` で「例: 30日」と書かれており確定していない。
あわせて、アップロードする画像の解像度・圧縮率・フォーマット(JPEG 想定)も未決。
これらは S3 のストレージコストと転送量に直結するため、OPS-05 と一緒に決める。

**サムネイルのサイズも同時に決める。** `03-web.md` §8 で、端末が本画像とサムネイルの2枚を
同一リクエストで送る方式に決定した。サムネイルは履歴画面のコマ列と1日分の一覧取得に使う。
履歴画面の表示サイズから逆算する(暫定: 長辺160px)。

なお、履歴画面が直近1週間を対象とするため、**保持期間は最低でも7日必要**。

### APP-04: Android アプリの詳細設計

カメラ/位置情報取得の実装方式、ローカルバッファの実装方式(Room か ファイル + メタデータか)、
Foreground Service の再起動耐性(端末再起動後の自動復帰、`BOOT_COMPLETED` の扱い)。

### APP-05: Web アプリの詳細設計

画面構成・状態モデル・API・署名付き URL の返し方は `03-web.md` で確定した
(状態管理は TanStack Query のみ、署名付き URL の有効期限は15分)。

残るのは実装レベルの選定のみ。UI ライブラリ/スタイリング手法、QR コードの描画ライブラリ、
テスト方針(コンポーネントテストの範囲、MSW を使うか)。

### OPS-01: ルートドメイン名の確定

構成は決定済み(`02-infra.md` §3)。ルートドメインを1つ取得してホストゾーンも1つとし、
`app.<root>` / `api.<root>`(prod)、`app.dev.<root>` / `api.dev.<root>`(dev)で環境を分ける。

残っているのは、実際に取得するドメイン名そのもの。取得先(Route53 で直接取るか、
外部レジストラで取って NS を向けるか)もあわせて決める。

### OPS-03: GitHub Actions のジョブ定義と Go Lambda のビルド方式

AWS 認証方式は決定済み(OIDC + plan/apply のロール分離、`02-infra.md` §8)。
残るのは実際のワークフロー YAML の構成と、Go Lambda のビルド/パッケージング方式
(`provided.al2023` ランタイム向けのクロスコンパイル、zip の作り方、ビルドキャッシュの効かせ方)。

### OPS-04: 監視・アラート方針

何を監視するか(Lambda エラー率、端末の未接続、S3 コスト急増など)、
通知先(メール、Slack など)。

### OPS-05: コスト試算

端末台数 × 送信間隔 × 画像サイズから、S3・DynamoDB・Lambda・データ転送のコストを試算する。
Cognito は Web User Pool 1つのみで、無料枠(月間アクティブユーザー数)に収まる想定。
APP-03 の画像仕様が決まらないと試算できない。
