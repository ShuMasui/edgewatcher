# EdgeWatcher 未決事項一覧

最終更新: 2026-08-24

設計の検討中に生じた論点を、決着まで含めてここに集約する。
**決着した論点も削除せず、状態を変えて残す。**過去の議論の参照を壊さないため、および
「なぜそれをやらなかったのか」が最も失われやすい情報であるため。

## 凡例

各項目は **ID / タイトル / 関係する書類 / 状態** の4つを持つ。

| 状態 | 意味 |
| --- | --- |
| `open` | 未着手。まだ議論していない |
| `pending` | 検討中、または暫定値で仮置きしている。`open` と行き来しうる |
| `decided` | 方針を決めた。決定内容は関係する書類に反映済み |
| `rejected` | 検討した上で「やらない」と決めた |
| `closed` | 前提の変化により論点自体が消滅した |

```text
open ⇄ pending ──→ decided
                └─→ rejected
                └─→ closed
```

`decided` / `rejected` / `closed` は終端であり、原則として戻らない。
前提が変わって蒸し返す場合は、新しい ID を採番して旧 ID から参照する。

### AUTH-04: セッショントークンとデバイスシークレットの有効期間 `open`

`06-auth.md` §3 では以下を暫定値としている。

- `sessionToken`: 12時間。端末は5〜15分間隔でアップロードするため、再取得は1日2回程度。
  短くすればトークン露出の窓が狭まるが `/device/token` の呼び出しが増える
- `deviceSecret`: 無期限(再ペアリングまで)。定期的なローテーションを入れるかは未定。
  入れる場合はアップロードのレスポンスに新しい secret を同梱する Pull 型が候補
- Cognito Web Pool 側のトークン有効期間(Access / ID / Refresh)も既定のままでよいか未確認

### AUTH-05: ペアリング開始のレート制限値と端末数上限値 `pending`

**上限の「伝え方」は 2026-08-24 に確定した**(`03-web.md` §1.9)。
常時カウンタ表示 + 上限時のバナーとボタン無効化、上限値は `GET /devices` のレスポンスで返す、
`PENDING` は台数に数え `ARCHIVED` は数えない。

残るのは数値そのもの。

- 端末数上限の暫定値は10台。APP-03 / OPS-05 のコスト試算と一緒に決める
- ペアリング開始のレート制限は暫定 10件/時。`POST /devices` は DynamoDB への書き込みのみで
  コスト面の切迫度は低いが、QR の総当たり試行の母数を抑えるために設ける

### AUTH-07: Google OAuth クライアントの本番設定 `open`

要求スコープが `openid` `email` `profile` のみで機微スコープを含まないため、Google の審査(verification)は
不要と見込んでいるが未確認。あわせて OAuth 同意画面のブランド設定(アプリ名・ロゴ・
プライバシーポリシーURL・利用規約URL)が必要になる。ポートフォリオ用途でこれらのページを
どこまで用意するか。

**Web ログインを Google SSO のみとしたため優先度が高い。** 代替のログイン手段が存在しないので、
ここが通らないと誰もログインできない。なお `profile` スコープはサイドバーのアバター画像に必要。

### AUTH-08: Web 側ログアウト時のトークン失効方針 `decided`

**決定(2026-08-24)**: ローカルのトークンを破棄したうえで、Cognito Hosted UI の `/logout` へ
リダイレクトしてセッション Cookie も破棄する。`GlobalSignOut` は呼ばない。

Refresh Token はそのブラウザのストレージにしか存在せず、破棄した時点で実質的に到達不能になるため。
一方、Hosted UI の `/logout` を省くと Cognito のセッション Cookie が残り、直後に「Google で続行」を
押すと無言で再ログインしてしまう。詳細は `03-web.md` §1.4.2。

### AUTH-09: 「応答なし」と判定する閾値 `pending`

状態モデル(`03-web.md` §1.3)により、「Web から切断された端末」と「単に圏外・電源断の端末」は
`status` で区別できる。残るのは、`PAIRED` のうち何秒受信がなければ「応答なし」と表示するかという閾値のみ。

暫定値は **送信間隔の3倍**(5分設定なら15分)。1回の送信失敗では応答なしにせず、
連続して落ちたときに初めて表示を変える意図。

### AUTH-10: 端末の共有・オーナー移管(Membership AR と Role 管理) `rejected`

**論点**: 複数名が1台のデバイスを閲覧したいという要望に備え、`Membership` 集約
(`userId` × `deviceId` × `role`)を持ち、ロール管理(閲覧のみ / 削除を含む全権限)を行うか。

**決定(2026-08-24)**: **行わない。1端末 = 1オーナーを確定仕様とする。**
`Device` が `ownerId` を直接持ち、オーナーの端末一覧は `ownerId` を PK にした GSI 1本で引く。
オーナー移管もスコープに含めない。

MVP では `Membership` は常に1レコードしか存在せず、全クエリがその中間層を経由することになる。
将来的に共有が必要になった場合は、その時点で `Membership` を導入してデータを移行する
(個人開発のデータ量であれば移行は現実的)。詳細は `engineering/domain-model.md` §1。

この決定により DATA-01 の前提が確定し、キー設計に着手できるようになった。

### AUTH-11: 監査ログの取得範囲 `open`

「誰がいつ端末を追加/削除したか」「ペアリングが何回失敗したか」を記録するか。
記録する場合の保存先(DynamoDB か CloudWatch Logs か)と保持期間。

### DATA-01: DynamoDB シングルテーブルの PK/SK・GSI 設計 `decided`

**決定(2026-08-24)**: PK / SK を `<TYPE>#<ID>` 形式で統一し、**1端末 = 1パーティション**に
集約する。GSI は2本(オーナー索引・ペアリングコード索引)。ID は ULID に統一し、
`observationId` の時刻ソート性をそのまま SK の並び順として使う。詳細は `engineering/dynamodb.md`。

要求したアクセスパターンはすべて充足済み(同 §5)。

### DATA-04: DynamoDB のバックアップ方針 `open`

PITR(ポイントインタイムリカバリ)を有効化するか。有効化するとストレージ量に応じた課金が
発生する一方、`ExportTableToPointInTimeAction` による S3 へのエクスポートが使えるようになり、
本番相当データを使ったデバッグが本番テーブルに負荷をかけずに行える。

観測レコードは TTL で自然に消えていく性質のデータであり、失われても再取得はできないが
致命的でもない。一方 Device レコードは失うとペアリングし直しになる。
この非対称性をどう扱うか(テーブル単位でしか設定できないため、実質は有効/無効の二択)。

### DATA-02: 削除された端末と観測レコードの物理削除方式 `decided`

**論点**: `DELETE /devices/{id}` で観測レコードまで同期的に消すのは、1端末あたり
最大288件あり、リクエスト内で消しきるのが現実的でないため。

**決定(2026-08-24)**: **論理削除を採る。** Device に `ARCHIVED` を含む4値の `status` を持たせ、
削除操作は `status = ARCHIVED` への更新と資格情報の失効に留める。
実体の削除は後日のスケジューリング処理でまとめて行う。

**このスケジューリング処理自体は今回のスコープに含めない。** MVP では `ARCHIVED` のレコードが
積み残る状態を許容する。

DATA-01 で観測レコードに TTL を張ることが決まったため、この負担はさらに小さくなった
(`engineering/dynamodb.md` §7)。画像本体は S3 のライフサイクルルールで、観測レコードは
DynamoDB の TTL で、それぞれ保持期間の経過後に自動削除される。掃除処理が扱う必要があるのは
`ARCHIVED` な Device アイテム本体のみで、これは端末台数ぶんしかない。

処理を実装する段になったら、手段(EventBridge Scheduler + Lambda / DynamoDB の TTL 属性 /
手動運用)を別 ID で検討する。

### DATA-03: ドメインモデルの集約構成 `decided`

**決定(2026-08-24)**: MVP の集約は `Device` と `Observation` の2つ。
`PairingSession` と `Credentials` は `Device` の内部、`User` 集約と `Membership` 集約は持たない。
`Recording` / `Stream` を束ねる共通の親集約(`Resource`)も置かない。

詳細と根拠は `engineering/domain-model.md`。

### APP-03: 画像の解像度・フォーマット・サムネイルサイズ `pending`

**サムネイルのサイズも同時に決める。** 端末が本画像とサムネイルの2枚を同一リクエストで送る方式に
決定した(`03-web.md` §3.7)。サムネイルは履歴画面のコマ列と一覧取得に使う。
履歴画面の表示サイズから逆算する(暫定: 長辺160px)。
