## 1. 機能要件

### 1.1 スコープ

余剰・格安の Android 端末を、屋外に常設する定点観測デバイスとして動作させる。
アプリの役割は「QR でペアリングし、以後カメラ画像と位置情報を定期送信し続けること」に尽きる。

観測データの閲覧は Web が担う。端末側で画像を見せるのは**画角を合わせるためのライブプレビューだけ**で、
直近に送った画像のサムネイルも表示しない。

### 1.2 画面構成

実質2画面。タブもナビゲーションドロワーも持たない。

| 画面 | 表示条件 | 内容 |
| --- | --- | --- |
| 未ペアリング | 資格情報を持たない | QR スキャナ(全画面) |
| ペアリング済み | 資格情報を持つ | 稼働状態、`[画角を合わせる]`、`[ログアウト]` のみ |

初回起動時は、未ペアリング画面に入る前に権限リクエストを通す(§1.3)。

### 1.3 権限

| 権限 | 用途 | 備考 |
| --- | --- | --- |
| `CAMERA` | 撮影 | 必須。拒否されると何もできない |
| `ACCESS_FINE_LOCATION` | 位置情報の付与 | 必須 |
| `POST_NOTIFICATIONS` | 常駐通知 | Android 13+ |
| `FOREGROUND_SERVICE_CAMERA` / `_LOCATION` | FGS の型宣言 | Android 14+。実行時要求は不要 |

**`ACCESS_BACKGROUND_LOCATION` は要求しない。** Foreground Service の `location` タイプが
「使用中」の状態を成立させるため不要であり、要求すると Play の審査で背景位置情報の
正当化が必要になる。限定配信であっても手間に見合わない。

権限が恒久的に拒否された場合は、その旨と「設定を開く」導線を出す。
権限なしで動作する縮退モードは持たない。カメラか位置情報のどちらかが欠けた時点で
このアプリの目的が成立しないため。

#### バッテリー最適化の除外

権限とは別に、**バッテリー最適化の対象から除外するようユーザーに促す。**
メーカー独自の省電力機構が Foreground Service を停止させることが実際に多く、
これを案内しないと「なぜか止まる」の主要因になる。

ペアリング完了直後に一度案内し、以後は稼働画面から再度開けるようにする。強制はしない。

### 1.4 ペアリング

1. Web が表示した QR をスキャンする(ペイロードは `ew1:<pairingCode>`)
2. `POST /device/pair` に `pairingCode` と端末情報を送る
3. 応答の `deviceSecret` を `EncryptedSharedPreferences` に保存する
4. `POST /device/token` でセッショントークンを取得する
   以後、アップロードが 401 または 403 を返したらここへ戻る(§1.9)
5. Foreground Service を開始し、定期送信に入る

詳細なサーバ側の処理は `06-auth.md` §2。

#### QR が引けなかったときの扱い

`pairingCode` の逆引きは GSI2 を経由し、**GSI は結果整合**である
(`engineering/dynamodb.md` §4)。QR 発行直後にスキャンすると伝播が間に合わない可能性がある。

そのため **1秒間隔で最大3回リトライ**してから失敗と判断する。
これは「待てば解決する空振り」であり、期限切れ・消費済みの QR とは区別する。
後者はサーバが明示的に返すため、即座に「この QR は使えません」と表示してよい。

### 1.5 定期送信

```text
タイマー発火(interval ごと。ウェイクロック + AlarmManager で担保。§3.0)
  → カメラを開く → 撮影 → 閉じる      ※プレビュー表示中はそのセッションを共有(§3.2)
  → 本画像 + サムネイル(長辺480px)を生成
  → observationId(ULID)を採番する    ※冪等性のため端末側で採番(`05-backend.md` §2.6)
  → 最後の既知位置を付与
  → ローカルに保存(画像はファイル、メタデータは Room)
  → 送信キューへ
  → POST /device/uploads(本画像とサムネイルを同一リクエストで送る)
  → 成功したらローカルから削除し、レスポンスの nextConfig を適用
```

- 送信間隔は 5 / 10 / 15 分。**値を決めるのは Web 側**で、端末はアップロードのレスポンスに
  同梱される `nextConfig` から受け取る(`00-overview.md` §6)。サーバは命令を push せず、
  端末が自発的に取得して適用する
- 設定変更は**最大1送信サイクル遅れて**反映される
- 位置情報は撮影のたびに取得するが、測位を待たない。最後の既知位置で十分であり、
  定点観測デバイスは動かない。実装は `FusedLocationProviderClient.lastLocation` で、
  `getCurrentLocation` は使わない(測位を待って撮影周期を引き延ばすため)。
  取得できなければ位置なしで送る。位置は必須項目ではない

#### 画像の仕様

| 項目 | 値 |
| --- | --- |
| 形式 | JPEG |
| 本画像 | 長辺 1600px / 品質 80 |
| サムネイル | 長辺 480px / 品質 75 |
| 本画像 + サムネイルの合計 | 4,500,000 バイト以下 |

合計が上限を超えたら、次の順に段階を落とす。**落としきっても超えるなら、その1枚は捨てる。**

1. 本画像の品質を 65 へ
2. 本画像の品質を 50 へ
3. 本画像を長辺 1280px / 品質 50 へ

サムネイルを 480px にしているのは、Web のダッシュボードが端末カードの画像に
`latestThumbnailUrl` を使っており、カード幅 280〜360px に対して 160px では
明確にぼやけるため。

### 1.6 プレビュー

ペアリング済み画面は、通常は**画像を一切表示しない。** `[画角を合わせる]` を押したときだけ
**ライブプレビュー**に切り替わり、もう一度押すと戻る。**トグルである。**

- ライブプレビュー中も定期送信は止まらない。同じカメラセッションから撮影する(§3.2)
- 常時ライブにはしない。カメラを開き続けると発熱し、屋外長期設置に向かない

**直近に送信した画像のサムネイルも表示しない。** 観測画像を見る場所は Web に一本化する。
端末側に出すと、保持期間・署名付き URL・履歴といった閲覧の仕組みが
端末側にも滲み出してくる。端末の責務は「送ること」であり、「見せること」ではない。
ライブプレビューだけが例外なのは、それが閲覧ではなく**設置作業のための道具**だからである。

### 1.7 稼働状態の表示

ペアリング済み画面と常駐通知の両方に、同じ情報を1行で出す。

| 状態 | 条件 | 表示 |
| --- | --- | --- |
| 観測中 | 直近の送信に成功 | 「観測中 / 最終送信 14:32」 |
| 送信待ち | 送信に失敗しバッファに滞留 | 「オフライン / 12件待機中」 |
| 観測停止中 | サービスが動いていない | 「停止中」+ [再開] |

**「オフライン」を明示するのは、画面を見ただけでは通信の成否が分からないため。**
屋外設置後にオーナーが端末を見に行く動機のほとんどが「本当に送れているのか」の確認であり、
その答えを最初に出す。

画面に置く要素はこの状態表示と `[画角を合わせる]`、`[ログアウト]` だけとする。
ただし **`停止中` のときだけ `[観測を再開]` を出す**。Android 14 以降は再起動後に
自動復帰できず(§1.10)、この操作がないとアプリから観測を再開する手段がなくなるため。

### 1.8 ログアウト

ペアリング済み画面のログアウトを押すと、確認ダイアログを挟んだうえで
`POST /device/logout` を呼び、ローカルの資格情報を破棄して未ペアリング画面へ戻る。

**確認を挟むのは Web と扱いが異なる。** Web のログアウトは再ログインが Google の
ワンクリックで済むが、端末のログアウトは `deviceSecret` を失うため、
**復帰には Web から QR を再発行して物理的に端末を操作し直す必要がある**(`06-auth.md` §6)。
取り返しのつきやすさが違う。

端末からの**削除**は提供しない。屋外に常設された端末が物理的に触られただけで
オーナーの管理下からレコードごと消える事態を避けるため。

### 1.9 401 と 403 を起点とした自己修復

サーバから 401 を受けたときの挙動だけで状態を回復する。プッシュ通知や別チャネルは持たない。

端末ルートでは、セッションが失効するとオーソライザが拒否し、API Gateway が
**403**(`{"message":"Forbidden"}`)を返す。401 は Authorization ヘッダそのものが
無い場合であり、日常運用で起きるのは 403 の方である。401 だけを見ていると
セッション失効から永久に回復できない。なお `POST /device/token` 自体の失敗は
すべて 401 であり、この一点では従来の記述と一致する。

```text
アップロードが 401 または 403
   └→ POST /device/token でセッション再取得を試みる
        ├─ 成功 → 新しい sessionToken で再送。以後継続
        └─ 401  → deviceSecret が無効(Web から切断されたか、端末が削除された)
                  ローカルの資格情報を全消去
                  Foreground Service を停止
                  未ペアリング画面へ戻り、理由を表示する
```

未ペアリング画面に戻す際、**なぜ戻されたのかを画面上に残す。**
「この端末は接続を解除されました。再度ペアリングしてください。」

黙って QR スキャナに戻ると、オーナーには端末の故障と区別がつかない。

### 1.10 再起動後の復帰

**Android 13 以下**: `BOOT_COMPLETED` を受けて Foreground Service を自動的に開始する。
オーナーの操作は要らない。

**Android 14 以上**: 自動復帰は**できない**。バックグラウンドから `camera` タイプの
Foreground Service を開始することが禁止されており、`BOOT_COMPLETED` の受信は
バックグラウンド起動に当たる(§3.4)。

この場合は `BOOT_COMPLETED` で**高優先度の通知だけを出す**。

> 「EdgeWatcher が停止しています。タップして観測を再開してください。」

通知をタップするとアプリが前面に出て、そこから Foreground Service を開始できる。

## 2. 非機能要件

### 2.1 対応環境

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| `minSdk` | 26(Android 8.0) | 余剰端末・格安端末を活用するコンセプト上、下限を低く取る |
| `targetSdk` | 最新 | Play の要件。引き上げを先送りすると新規アップロードが通らなくなる |
| 画面の向き | 縦固定 | 設置後に回転する必要がなく、プレビューの実装も単純になる |

`minSdk` と `targetSdk` の幅が広いため、**Foreground Service 周りは OS バージョンによる
分岐を前提に設計する**(§1.10、§3.4)。

### 2.2 常時稼働

- **常時給電を前提とする。**省電力のための機能制限は設けない(`00-overview.md` §5)
- 常駐通知が出続けることは許容する
- **画面 OFF でも動作し続けること。**Foreground Service だけでは足りず、
  ウェイクロックと `AlarmManager` の二重化で担保する(§3.0)
- カメラは撮影時とプレビュー表示中のみ開く。発熱を避けるため常時保持しない
- プロセスが OS に落とされた場合に備え、サービスは `START_STICKY` で再生成させる

### 2.3 データ保持(オフラインバッファ)

**288件(5分間隔で24時間相当)または 500MB のいずれか先に達したら、古いものから削除する。**

- 件数だけで制限すると、高解像度設定でストレージを圧迫する
- 容量だけで制限すると、低解像度設定で保持期間を超えた画像を大量に抱える
- 両方置くことで、どちらの設定でも破綻しない

**バッファ上限を保持期間より長くしても意味がない。** 観測レコードの TTL は
`capturedAt` を基準に決まるため(`engineering/dynamodb.md` §7)、長時間オフラインだった端末が
古い画像を送っても、サーバ到着時点で期限切れになりうる。

### 2.4 通信

- 送信失敗時は**指数バックオフでリトライ**する
- リトライ中も定期撮影は止めない。撮った画像はバッファに積まれる
- バッファが上限に達するまでは observation を失わない
- **同じ observation を再送しても記録は1つに保たれる。**`observationId` を端末側で採番して
  リクエストに含めるため、応答を受け取れずにリトライしても二重記録にならない
  (`05-backend.md` §2.6)
- `413`(ペイロード超過)はリトライ不能な失敗として扱い、バッファから捨てる。
  再送しても永久に通らないため

### 2.5 セキュリティ

- `deviceSecret` と `sessionToken` は `EncryptedSharedPreferences` に保存する
- `deviceSecret` はセッションの再取得にしか使わない。日常のアップロードには
  `sessionToken` を使い、長期資格情報の露出頻度を下げる(`06-auth.md` §3)
- 資格情報をログに出力しない
- 通信は HTTPS のみ

### 2.6 テスト方針

**JVM のユニットテストだけを書く。計装テストと Robolectric は書かない。**

対象は、間違えるとサーバ側のデータが壊れる判断に限る。

| # | 対象 |
| --- | --- |
| 1 | ULID の採番時刻が `capturedAt` と一致する |
| 2 | HTTP status → 失敗種別の分類(とくに 401 と 403) |
| 3 | バッファの eviction(288件 / 500MB の先着) |
| 4 | 送信順序(最新1枚 → 以後古い順) |

カメラ・位置情報・通知・Foreground Service の挙動は、エミュレータでも実機の
省電力機構を再現できず、テストが通っても現地で止まる。ここは実機を常時給電で設置しての
受け入れ確認でまとめて見る(`superpowers/specs/2026-09-10-android-app-design.md` §11)。

## 3. 設計判断

### 3.0 画面 OFF 中にタイマーを止めない

**Foreground Service は CPU のスリープを妨げない。** 画面を消すと端末はサスペンドに入り、
`Handler.postDelayed` やコルーチンの `delay` といったプロセス内タイマーは発火しないか大幅に遅延する。
Foreground Service は「プロセスが殺されにくい」ことを保証するだけで、「動き続ける」ことは保証しない。

したがって、次の二重化を行う。

| 仕組み | 役割 |
| --- | --- |
| `PARTIAL_WAKE_LOCK` | サービス稼働中は保持し続け、CPU のサスペンドを止める |
| `AlarmManager`(`setExactAndAllowWhileIdle`) | 次回撮影時刻に必ず起こす。プロセスが落ちて再生成された場合の復帰点にもなる |

ウェイクロックを常時保持できるのは、**常時給電を前提としているため**である
(`00-overview.md` §5)。バッテリー駆動なら選べない設計だが、本プロジェクトでは
電力より確実性を優先してよい。CPU は起きているだけで実際の処理は5分に一度なので、発熱も小さい。

`AlarmManager` を併用するのは、ウェイクロックがメーカー独自の省電力機構に剥がされた場合や、
プロセスが OS に落とされて `START_STICKY` で作り直された場合に、
**次の撮影時刻から確実に復帰できる足場**を残すため。タイマーを1本に頼らない。

Android 12 以降、`setExactAndAllowWhileIdle` には `SCHEDULE_EXACT_ALARM` の許可が要る。
これはバッテリー最適化の除外(§1.3)と同じタイミングで案内する。

#### Doze は本件では発動しない

Doze の条件は「画面 OFF + 静止 + **バッテリー駆動**」である。常時給電の本プロジェクトでは
条件を満たさないため、Doze による遅延は考慮しなくてよい。給電が切れた時点で観測自体が
成立しなくなるため、Doze 下での動作を作り込む意味もない。

### 3.1 WorkManager を使わない

`WorkManager` の `PeriodicWorkRequest` は OS 側の制約で**最短間隔が15分**であり、
5分・10分間隔の定期実行を実現できない。

そのため **Foreground Service + 自前のタイマー**方式を採る。専用ハードウェアとして
常時稼働させる前提のため、常駐通知が表示されることは許容する(`00-overview.md` §7)。

ただし自前のタイマーはプロセス内の `delay` だけでは成立しない。画面 OFF 中に止まるため、
ウェイクロックと `AlarmManager` で支える必要がある(§3.0)。
`WorkManager` を捨てた代償として、OS が面倒を見てくれていた「確実に起こす」部分を
自分で持つことになる、という理解が正しい。

### 3.2 カメラの所有権は Foreground Service が持つ

**Android のカメラは同時に2つのクライアントが開けない。** サービスが5分ごとに撮影する一方で、
画面側が独立してライブプレビューを開こうとすると競合する。

したがってカメラの所有権はサービスに一本化し、画面はサービスに**プレビュー用の Surface を
渡す**形にする。プレビュー表示中は、定期撮影も同じセッションから行う。

この形にすると、プレビューのために定期送信を一時停止する必要がない。
「プレビューを開いている間だけ観測に穴が開く」という分かりにくい挙動を避けられる。

**カメラ API は CameraX を使う。Camera2 は使わない。** 所有権を一本化するこの設計では
`ProcessCameraProvider` の bind / unbind がそのまま所有権の付け外しになり、
プレビューの ON / OFF は `ImageCapture` を bind したまま `Preview` だけを
足し引きすればよい。Camera2 だと同じことをセッションの再構成として自前で書くことになる。
サービスを `LifecycleService` にしているのは、CameraX が `LifecycleOwner` を要求するため。
その結果カメラの寿命がサービスの寿命と一致し、画面を閉じても観測が続く。

### 3.3 画像はファイル、メタデータは Room

画像本体をアプリ専用ストレージのファイルとして置き、Room には
`id` / `capturedAt` / `imagePath` / `thumbPath` / `lat` / `lng` / 送信状態 だけを持つ。

BLOB を SQLite に入れると DB ファイルが肥大し、削除しても領域が戻りにくい。
バッファは常に書いては消すことを繰り返すため、この性質が効いてくる。

### 3.4 Foreground Service の型と OS バージョン

Android 14 以降、Foreground Service には型の宣言と対応する権限が要る。
本アプリは `camera` と `location` の両方を使う。

**`camera` 型はバックグラウンドから開始できない。** これは §1.10 の再起動後の復帰に直撃し、
回避策がない。型を `dataSync` に変えても解決しない。カメラは「使用中のみ」権限であり、
`camera` 型の FGS がその「使用中」を成立させているためである。

古い端末ほど完全自動で動く、という皮肉な結果になる。これはコンセプト
(余剰端末の活用)とは相性が良い。

### 3.5 復旧時は最新の1枚を先に送る

長時間オフラインから復帰したとき、単純な FIFO で古い順に送ると、
Web のダッシュボードには何時間も前の画像が出続ける。

そのため**最新の1枚を先に送り、そのあと残りを古い順に送る**。
オーナーが最初に知りたいのは「今どうなっているか」であり、それが即座に反映される。

この順序はサーバ側の非正規化に影響する。遅れて届いた古い画像が
`Device.latestThumbnailKey` を巻き戻さないよう、サーバは条件付き更新を行う
(`engineering/dynamodb.md` §5.1)。

### 3.6 端末側 UI を最小に保つ理由

設定項目を端末側に持たせない。送信間隔も Web から配る。

屋外に設置された端末を操作するには物理的にそこへ行く必要があり、
**端末でしか変えられない設定があると、設置場所まで足を運ばないと運用できなくなる。**
端末側の UI は「今ちゃんと動いているか」と「何が写っているか」の確認に限定する。

## 4. モック

`docs/mocks/native-mocks.html` に、ビルド不要の HTML でモックを置く。
Web のモックと同じくシナリオ切替式で、スマートフォンの縦画面フレームに描画する。

機能要件の記述とモックのシナリオは1対1で対応させ、要件を変えたらモックも同時に更新する。
