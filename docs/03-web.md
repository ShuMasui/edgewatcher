## 1. 機能要件

### 1.1 スコープ

オーナーが自分の Android 端末を登録・管理し、それらが送ってくる観測画像を閲覧する。
地図表示・画像解析・端末の共有はスコープ外(`00-overview.md` §3)。

### 1.2 画面とルーティング

| ルート | 画面 | 認証 |
| --- | --- | --- |
| `/login` | ログイン | 不要 |
| `/` | 最新画像一覧(ダッシュボード) | 必要 |
| `/devices/:deviceId/history` | 履歴(スクラバー。1日単位で遡れる) | 必要 |
| `/devices` | 端末一覧 | 必要 |

未認証で認証必須ルートに来た場合は `/login` へリダイレクトし、ログイン後に元のルートへ戻す。

ペアリングは独立したルートを持たせず、端末一覧上のモーダルとして表示する。
QR は最長5分しか存在しない一時的なものであり、URL で共有・再訪できる場所に置く意味がないため。

#### サイドバー

常設で3要素のみ。

- 「最新画像」— `/` へ
- 「端末一覧」— `/devices` へ
- 最下部にアバターボタン(Google のプロフィール画像)。クリックでポップオーバーを開く(§1.4.2)

### 1.3 端末の状態モデル

一覧の表示・行ボタンの切り替え・認証設計の三方に効くため、状態を先に定義する。

| 表示 | サーバ側の条件 | 行のボタン |
| --- | --- | --- |
| ペアリング待ち | `status = PENDING` | **[QR を表示]** |
| 接続中 | `status = PAIRED` かつ 最終受信が閾値内 | **[セッション切断]** |
| 応答なし | `status = PAIRED` かつ 最終受信が閾値超過 | **[セッション切断]** |
| 切断済み | `status = DISCONNECTED` | **[再ペアリング]** |

`status = ARCHIVED`(オーナーが削除した端末)は一覧に**表示しない**。物理削除は後日の
スケジューリング処理で行うためレコードは残るが、Web からは存在しないものとして扱う
(`00-overview.md` §5、`01-openquestion.md` DATA-02)。

上記に加え、**有効な PairingSession がぶら下がっている端末は、`status` によらず [QR を表示] になる**。
これが「初回ペアリング中」と「再ペアリング中」の両方を表す。ボタンの enable / disable を
UI 側で個別に管理する必要がなく、状態から一意に導出される。

この状態モデルにより、「Web から切断した端末」と「単に圏外・電源断の端末」を、
最終受信時刻の推測ではなく `status` で明確に区別できる。残る未確定は「応答なし」と判定する閾値のみで、
暫定値は **送信間隔の3倍**とする(`01-openquestion.md` AUTH-09)。

### 1.4 ログインとログアウト

#### 1.4.1 ログイン

- 「Google で続行」ボタン1つのみ。メール/パスワードのフォームもサインアップ画面も持たない
- Cognito Hosted UI へリダイレクトし、Google の認可を経てコールバックで戻る
- 認証済みの状態でこの画面に来た場合は `/` へリダイレクトする

#### 1.4.2 ログアウト

サイドバー最下部のアバターボタンをクリックすると、その右上に**ポップオーバー**が開く。

- 中身はメールアドレス1行と「ログアウト」1項目のみ
- 外側クリックまたは `Esc` で閉じる
- **確認ダイアログは挟まない。**ログアウトは破壊的操作ではなく、再ログインも Google のワンクリックで
  完了するため、確認は摩擦にしかならない

「ログアウト」を押したときの処理は、以下の順序で行う。

1. TanStack Query のキャッシュを全破棄する
2. ローカルに保持しているトークンを破棄する
3. Cognito Hosted UI の `/logout?client_id=...&logout_uri=<app>/login` へリダイレクトする

**3 が必須である理由**: ブラウザのトークンを破棄するだけでは Cognito 側のセッション Cookie が残り、
直後に「Google で続行」を押すと何のプロンプトも出ずに即再ログインしてしまう。
ユーザーにはログアウトが効いていないように見える。

**1 を最初に置く理由**: 別アカウントでログインし直したときに、前のユーザーの端末一覧が
キャッシュから一瞬描画される事故を防ぐ。リダイレクトで結果的にページは破棄されるが、
キャッシュの寿命をセッションの寿命に明示的に揃えておく。

Cognito の `GlobalSignOut` は呼ばない。Refresh Token はそのブラウザのストレージにしか存在せず、
2 の時点で実質的に到達不能になるため(`01-openquestion.md` AUTH-08)。

### 1.5 ダッシュボード(最新画像一覧)

- 登録端末をカードのグリッドで表示。カードの内容は最新画像・端末名・状態バッジ・撮影時刻
- **60秒ごとに再取得**する。送信間隔が最短5分であるため、これより短い間隔で引く意味がない
- カードをクリックすると、その端末の履歴画面へ遷移する
- まだ一度も画像が届いていない端末(ペアリング待ち等)は、画像の代わりに状態を示すプレースホルダを出す
- 端末が0台のときは空状態を表示し、「端末を追加」への導線を出す
- 60秒ごとの再取得が失敗した場合の振る舞いは §1.10.3 に定める

### 1.6 履歴(スクラバー)

- 中央に1枚を大きく表示。下に時刻スライダーと、現在位置の近傍サムネイルのコマ列
- 再生ボタンでタイムラプス再生
- 上部に日付ナビゲーション(`‹ 8/23 ›`)。初期表示は当日で、初期位置は最新の画像
- コマ列とスライダーはサムネイルを使い、中央の大表示のみ本画像を都度取得する
- その日の観測データが0件の場合は、コマ列の代わりに「表示できる画像がありません」を表示する

#### スクラバーは常に1日、遡れる範囲は保持期間

**スライダーが扱うのは常に1日分**(5分間隔で最大288枚)。過去に遡るのは日付ナビで行い、
遡れる日数は**サーバが返す `retentionDays` で決まる**(dev は当日のみ、prod は7日)。
最古の日まで来たら `‹` を無効化し、「これより前の画像は保持期間を過ぎています」と添える。

保持期間ぶんを1本のスライダーに載せる案は採らない。prod の7日は5分間隔で2016枚あり、
1コマあたり1px未満になって目的の時刻に合わせられないため。1日単位なら
スライダーの粒度が実用的な範囲に収まり、取得も常に1リクエストで済む。

**`retentionDays` は UI にハードコードしない。** 環境ごとに異なる値であるため、
`GET /app-config` から受け取る(§3.8)。

#### 表示範囲はクエリ側で固定する

S3 ライフサイクルと DynamoDB TTL はいずれも**遅延削除**であり、保持期間を過ぎたデータが
しばらく残る(§2.1)。「あるものを全部出す」作りにすると、遡れる範囲が日によって伸び縮みする。

クエリは常に「指定された日の 00:00〜24:00」で発行し、日付ナビの下限も `retentionDays` から
計算した固定値とする。実際にデータが残っているかどうかで挙動を変えない。

### 1.7 端末一覧

表形式。列は「端末名 / 状態 / 最終受信 / 送信間隔 / 操作」。

- 送信間隔は行内のセレクトで変更できる(5分 / 10分 / 15分)。変更は Pull 型で配信されるため、
  最大1送信サイクル遅れて反映される旨を UI に添える(`00-overview.md` §6)
- 操作列は §1.3 の状態依存ボタン1つと、⋮ のオーバーフローメニュー
- ⋮ の中身は「名前の変更」「削除」。削除は取り返しがつかないため確認ダイアログを挟む
- 右上に「端末を追加」ボタン
- トップバーに登録数を「**3 / 10 台**」の形式で表示する(§1.9)

### 1.8 ペアリング

#### 1.8.1 端末を追加(初回)

1. 「端末を追加」→ モーダルで端末名を入力(例: 「玄関」)
2. `POST /devices` → Device レコードが `status = PENDING` で作られ、同時に PairingSession が発行される
3. モーダルに QR と残り時間のカウントダウンを表示。2秒間隔でポーリング
4. 端末がスキャンすると `status = PAIRED` になり、モーダルは「接続しました」に変わる
5. モーダルを閉じると一覧に反映される

端末名を先に入力させるのは、`status = PENDING` の行が一覧に即座に出るため、
名前がないと何の行なのか判別できなくなるため。

#### 1.8.2 QR の期限切れ

残り時間が0になったら QR を伏せ、「有効期限が切れました」と再発行ボタンを出す。
再発行は `POST /devices/{id}/pairing-sessions` を呼ぶだけで、Device レコードは作り直さない
(`deviceId` は不変)。

#### 1.8.3 再ペアリング

「切断済み」の端末の [再ペアリング] を押すと、同じモーダルが `deviceId` 指定で開く。
`deviceId` が変わらないため、**端末を初期化しても別の Android 端末に置き換えても、
過去の画像履歴が同じ観測地点として繋がり続ける**。

#### 1.8.4 ペアリング待ちのまま放置された端末

QR を発行したまま一度もスキャンされなかった端末は `status = PENDING` の行として一覧に残る。
自動削除はせず、オーナーが ⋮ から削除する。自動で消すと、オーナーが端末を取りに行っている間に
行が消えるという挙動になり、かえって分かりにくいため。

### 1.9 端末数の上限

1オーナーが登録できる端末数には上限を設ける(`01-openquestion.md` AUTH-05。上限値は未確定、暫定10台)。
伝え方は以下に確定する。

- 端末一覧のトップバーのカウントを「**3 / 10 台**」形式にし、**残り枠を常時可視化**する。
  上限に近づく過程が見えるため、到達が不意打ちにならない
- 上限に達したら、表の上に説明バナーを出す
  (例: 「端末の上限(10台)に達しています。追加するには既存の端末を削除してください。」)
- 同時に「端末を追加」ボタンを**無効化**する。理由がバナーとして同じ画面に見えているため、
  無効化しても行き止まりにならない
- **`PENDING` の端末も1台として数える。** DynamoDB にレコードが存在し、
  QR 総当たりの母数にもなるため。これは AUTH-05 で上限を設ける動機そのものである
- **`ARCHIVED` の端末は数えない。** レコードは物理削除まで残るが、オーナーから見れば
  削除済みであり、台数に数えると「削除したのに枠が空かない」ことになる。
  台数の算出条件は `status ∈ {PENDING, PAIRED, DISCONNECTED}`
- **上限値はサーバから返す。** `GET /app-config` の `deviceLimit` を使い、UI にハードコードしない(§3.8)。
  なお**現在の登録台数は `/app-config` には入らない**。ユーザーごとに異なる値であり、
  `GET /devices` の結果を数えて得る

上記の事前抑止に加え、`POST /devices` が 429 を返した場合の処理も残す。
2つのタブで同時に追加操作を行った場合に競合しうるため。表示は §1.10.4 に従う。

### 1.10 エラー時の振る舞い

エラーは種類ごとに**受け止める層を分ける**。原則は「**ユーザーが行動できる場所に出す**」。

| 層 | 対象 | 見せ方 |
| --- | --- | --- |
| HTTP クライアント | 401 | 画面に出さない。トークン破棄 → `/login`(戻り先パスを保持) |
| ルート | 403 / 404 | 「この端末は見つかりません」+ 一覧へ戻る導線 |
| クエリ(GET) | 5xx / ネットワーク断 | 画面内にインライン + [再試行]。既存データは消さない |
| ミューテーション | 4xx / 5xx | 操作の起点(モーダル・行)のすぐ近くにインライン |
| 画像 | S3 の 403 | ユーザーに見せず自動回復 |

#### 1.10.1 認証切れ(401)

HTTP クライアント層で捕捉し、コンポーネントには一切漏らさない。
ローカルのトークンを破棄して `/login` へ送り、ログイン後に元のルートへ戻す。

全画面に等しく起こりうるエラーであり、各コンポーネントで個別に扱うと必ず漏れが出るため、
唯一の共通経路である HTTP クライアントに置く。

#### 1.10.2 対象が存在しない(403 / 404)

削除済みの端末の履歴 URL を直接開いた場合などに起きる。
`/devices/:deviceId/history` のルート単位で受け、「この端末は見つかりません」と
端末一覧へ戻る導線を出す。

オーナー不一致(403)も同じ表示にする。他人の `deviceId` の存在有無を
エラーの出し分けから推測されないようにするため。

#### 1.10.3 取得の失敗(5xx / ネットワーク断)

画面内にインラインで表示し、[再試行] ボタンを添える。**既に表示されているデータは消さない。**

- **初回ロードで失敗した場合**: 画面中央にエラーと [再試行]
- **ダッシュボードの60秒ポーリングが失敗した場合**: 既存の画像を保持したまま、
  トップバーに小さく「更新できていません(最終更新 14:32)」とだけ出す

後者を特に定めるのは、「今の状態」を確認する定点観測の画面が、通信が一瞬切れるたびに
空になるのが最も避けたい挙動であるため。古い画像でも、撮影時刻が添えられていれば十分に役に立つ。

自動リトライは**指数バックオフで最大2回**とする。TanStack Query 既定の3回は、
5分間隔でしか更新されないデータに対して過剰。

#### 1.10.4 操作の失敗(ミューテーション)

操作の起点のすぐ近くに出す。モーダル内の操作ならモーダル内、行内の操作ならその行に。

| 操作 | エラー | 表示場所と内容 |
| --- | --- | --- |
| 端末を追加 | 429(上限) | モーダル内。「上限に達しています」+ 端末一覧へ戻る導線 |
| QR ポーリング | 409(消費済み/期限切れ) | モーダルを期限切れ表示に切り替え、[QR を再発行] を出す |
| 名前の変更 | 4xx / 5xx | モーダル内。入力値は保持する |
| 送信間隔の変更 | 4xx / 5xx | その行にインライン。セレクトを元の値に戻す |
| セッション切断 / 削除 | 4xx / 5xx | 確認ダイアログ内に表示し、ダイアログは閉じない |

**ミューテーションは自動リトライしない。** `POST /devices` が二重に走ると端末が2台できてしまう。
再試行はユーザーの明示的な操作に限る。

#### 1.10.5 署名付き URL の失効

署名付き URL の有効期限は15分であり、履歴画面を開いたまま放置すると必ず失効する。
S3 は 403 を返すが、**これはユーザーに見せず自動で回復させる。**

`<img>` の `onError` で検知し、該当クエリを invalidate して URL を取り直し、1回だけ再描画する。
再取得後も失敗した場合に限り、画像の代わりにプレースホルダを出す。

#### 1.10.6 トースト機構を持たない

上記のすべてに「エラーを置くべき具体的な場所」が存在するため、汎用のトースト基盤は導入しない。
トーストは時間で消えるため、データが表示できていない画面のエラーとは特に相性が悪い
(消えた後に画面には何も残らない)。

## 2. 非機能要件

本節は現時点で確定している範囲のみを記す。未着手の観点は §5 に挙げる。

### 2.1 性能・データ量

| 項目 | 要件 | 根拠 |
| --- | --- | --- |
| ダッシュボードの更新間隔 | 60秒 | 端末の送信間隔が最短5分のため、これより短く引く意味がない |
| 画像の保持期間 | **dev 1日 / prod 7日** | dev はコスト最小化、prod はデモとして十分な長さを確保。S3 ライフサイクルと DynamoDB TTL の両方に同じ値を設定する |
| 履歴の1回の取得単位 | 1日(最大288件) | スライダーの粒度と取得量の両方が実用的な範囲に収まる |
| 履歴を遡れる範囲 | `retentionDays`(`/app-config`) | 保持期間と揃える。UI にハードコードしない |
| 履歴のコマ列・一覧 | サムネイルを使用 | 本画像を288件分読むことを避ける |
| 本画像の取得 | 表示する1枚ごとに都度 | 同上 |
| 署名付き URL の有効期限 | 15分 | 閲覧セッションの想定長。§1.10.5 の自動回復とセット |

### 2.2 可用性・回復性

- 通信断からの回復時、ユーザーの操作なしに次のポーリングで自動復帰すること(§1.10.3)
- 通信断の間、既に取得済みのデータを画面から消さないこと
- 署名付き URL の失効はユーザーに露出せず自動回復すること(§1.10.5)
- サーバ側の状態を唯一の情報源とし、クライアントに永続的な状態を持たないこと(§3.2)

### 2.3 セキュリティ

- 全 API が API Gateway の JWT オーソライザ(Cognito Web Pool)を通ること
- Lambda 側で JWT の `sub` と対象リソースの `ownerId` の一致を毎回確認すること(`06-auth.md` §7)
- 画像バケットは非公開とし、参照は署名付き URL のみ(`02-infra.md` §7)
- 配信は CloudFront + OAC による HTTPS のみ。S3 の静的ウェブサイトホスティングは使わない
- 他オーナーのリソースについて、存在の有無をエラーの出し分けから推測できないこと(§1.10.2)
- ログアウト時に Cognito のセッション Cookie まで破棄すること(§1.4.2)

### 2.4 対応環境

- モダンブラウザの最新版(Chrome / Safari / Firefox / Edge)を対象とする。IE および
  レガシーブラウザは対象外
- 主たる利用環境はデスクトップ。画面幅の下限とモバイル対応の程度は未確定(§5)

### 2.5 アクセシビリティ

- 操作可能な要素はキーボードで到達・実行できること
- モーダルとポップオーバーは `Esc` で閉じられること
- **無効化されたボタンの理由を、ツールチップのみで説明しないこと。**
  タッチデバイスから到達できないため、理由は同じ画面に常設の要素として表示する(§1.9 のバナー)

## 3. 設計判断

### 3.1 構成

- React + Vite の SPA。S3(非公開)+ CloudFront(OAC)で静的配信(`02-infra.md` §7)
- ルーティングは React Router
- サーバ状態は **TanStack Query のみ**で管理する

### 3.2 グローバルストアを置かない理由

この画面群が扱う状態は、端末一覧・観測データ・ペアリング状況とほぼ全てがサーバ由来であり、
TanStack Query のキャッシュがそのまま単一の情報源になる。クライアント固有の状態は
スクラバーの再生位置程度しかなく、これはコンポーネントローカルで足りる。
グローバルストアを足すと、同じデータがキャッシュとストアの2箇所に存在して同期の責務が生まれる。

### 3.3 エラーを階層で分ける理由

§1.10 の6種類のエラーは、必要な扱いが互いに大きく異なる。401 は画面を離脱させるべきで、
署名付き URL の失効はユーザーに見せる必要すらなく、上限超過は「何をすれば解決するか」を
伝える必要がある。これらを単一の仕組み(例えばトースト一本)で処理すると、どれかが必ず不適切になる。

一方、Error Boundary に寄せて例外として投げ上げる方式も検討したが、
名前変更の 409 のような局所的な失敗で画面全体がフォールバックに差し替わるのは過剰であり、
結局どの例外を境界まで通すかを選別することになる。層で分けるほうが直接的である。

### 3.4 セッション切断の意味

`06-auth.md` §6 で定義したとおり、Web からの「セッション切断」は
**`sessionTokenHash` と `deviceSecretHash` の両方を無効化し、`status` を `DISCONNECTED` にする**操作である。

セッショントークンだけを失効させると、端末は 401 を受けたあと `deviceSecret` を使って
数秒で新しいセッションを取得してしまい、切断にならない。

端末側は次回の `/device/token` で 401 を受け、`06-auth.md` §5 の自己修復により
ローカル資格情報を破棄して未ペアリング画面に戻る。

3つの操作の違い:

| 操作 | 実行主体 | Device レコード | 画像履歴 | 復帰方法 |
| --- | --- | --- | --- | --- |
| セッション切断 | Web | 残る(`DISCONNECTED`) | 残る | 再ペアリング |
| ログアウト | 端末 | 残る(`DISCONNECTED`) | 残る | 再ペアリング |
| 削除 | Web | `ARCHIVED`。後日物理削除 | 後日物理削除 | なし(新規登録) |

削除は論理削除だが、**オーナーから見た挙動は物理削除と区別がつかない**。一覧から消え、
履歴 URL は 404 になり、台数の枠も空く(§1.9)。レコードが残るのは後始末を
スケジューリング処理に委ねるための実装都合であり、UI 上に「アーカイブ済み」のような
状態を見せることはしない。

ログアウトとセッション切断はサーバ側の結果が同じで、違いは実行主体だけ。
端末側でログアウトするとローカルの `deviceSecret` が失われ、端末単独では復帰できないため、
サーバ側も同じく資格情報を失効させて `DISCONNECTED` に揃える(`06-auth.md` §6)。

### 3.5 API(Web 向け)

```text
GET    /app-config                            環境定数(retentionDays / deviceLimit / intervalOptions)
GET    /devices                               一覧
POST   /devices                               端末を追加(名前) → Device(PENDING) + QR発行
POST   /devices/{id}/pairing-sessions         再ペアリング / QR 再発行
GET    /devices/{id}/pairing-sessions/latest  ポーリング用(2秒間隔)
POST   /devices/{id}/disconnect               セッション切断(資格情報を失効)
PATCH  /devices/{id}                          端末名 / 送信間隔の変更
DELETE /devices/{id}                          削除
GET    /devices/{id}/observations?date=       指定日の観測(時刻 + サムネイルの署名付きURL)
GET    /observations/{id}/image               本画像の署名付きURL
```

いずれも API Gateway の JWT オーソライザ(Cognito Web Pool)を通り、
Lambda 側で JWT の `sub` と対象リソースの `ownerId` の一致を毎回確認する(`06-auth.md` §7)。

### 3.6 署名付き URL の返し方

一覧および1日分の観測データには、サムネイルの署名付き URL をレスポンスに同梱する。
署名の生成は S3 への通信を伴わない純粋な計算のため、件数が増えてもレイテンシに影響しない。
一方、本画像の URL は表示する1枚ごとに都度取得する。1日分(最大288件)の本画像 URL を
まとめて返すとレスポンスが数十 KB 膨らむのに対し、実際に表示されるのはごく一部であるため。

### 3.7 サムネイルの生成場所

スクラバーのコマ列と1日分の一覧取得には小さい画像が必要になる。
**Android 端末が撮影時に本画像とサムネイルの2枚を同一リクエストで送る**方式を採る。

S3 イベントから Lambda を起動して生成する構成が一般的だが、その場合は
画像デコードを行う Lambda・S3 イベント設定・生成が完了するまでの間の表示不整合を抱えることになる。
端末側は既にビットマップをメモリに持っており、縮小は数ミリ秒で終わる。
追加の転送量は1枚あたり 10KB 程度で、送信間隔を考えれば無視できる。

この決定は `04-native.md`(アップロード仕様)と `05-backend.md`(S3 のキー設計)の前提になる。

### 3.8 環境定数を `/app-config` で配る

`retentionDays` や `deviceLimit` のように、**環境ごとに決まり、全ユーザーで同一で、
デプロイでしか変わらない**値は、専用エンドポイント `GET /app-config` にまとめて配る。

```json
{
  "retentionDays": 7,
  "deviceLimit": 10,
  "intervalOptions": [5, 10, 15]
}
```

#### 端末一覧のレスポンスに混ぜない理由

**キャッシュのライフサイクルが違う。** ダッシュボードは60秒ごとに `GET /devices` を引くが、
環境定数はデプロイまで変わらない。同梱すると、同じレスポンスに `staleTime: 60秒` と
`staleTime: Infinity` という相反するキャッシュ方針を要求することになる。

**偽の依存が生まれる。** 履歴画面は端末1台の画面であるにもかかわらず、`retentionDays` を
知るためだけに全端末のリストへ依存することになる。

`/app-config` は起動時に1回だけ取得し、セッション中は再取得しない。デプロイで値が変われば
新しいバンドルが配信されてページが読み直されるため、それで足りる。

#### 収録の基準

**「環境ごとに決まり、全ユーザーで同一か」**を基準にする。これを外すと、じきに何でも入る袋になる。

- 入る: `retentionDays`、`deviceLimit`、`intervalOptions`
- 入らない: **現在の登録台数**(ユーザーごとに異なる。`GET /devices` の結果を数える)

将来 `deviceLimit` をプラン別にするなら、その時点で `/app-config` から出して
ユーザーのリソース側へ移す。この判断も同じ基準から導かれる。

#### 端末向けの設定とは経路を分ける

このシステムには設定の配送チャネルが2つあり、**統合しない**。

| 配る先 | 経路 | 中身 |
| --- | --- | --- |
| Web UI | `GET /app-config`(起動時に1回) | `retentionDays` / `deviceLimit` / `intervalOptions` |
| Android 端末 | アップロードのレスポンスの `nextConfig`(Pull 型) | 送信間隔、将来は解像度・圧縮率 |

端末は必ず定期的にサーバへ来るため専用エンドポイントを必要とせず(`00-overview.md` §6)、
逆に Web は端末の送信サイクルを待てない。両者は同じ Terraform 変数から派生するが、
配送の性質が異なる。

なお `/app-config` も**通常どおり JWT オーソライザを通す**(§2.3)。非機密の定数ではあるが、
「全 API が JWT オーソライザを通る」という不変条件に例外を作らない。
ログイン画面はこの値を必要としないため、認証必須にしても支障がない。

## 4. モック

`docs/mocks/web-mocks.html` に、ビルド不要の HTML でモックを置く。
1ファイルの中に全画面を持ち、左側のシナリオリストで状態を切り替えられる構成とする。
画面を跨ぐ状態遷移を1つのファイルで見せるため、画面ごとにファイルを分けていない。

シナリオは正常系だけでなく、§1.10 のエラー時の振る舞いと §1.9 の上限到達も含む。
機能要件の記述とモックのシナリオは1対1で対応させ、要件を変えたらモックも同時に更新する。
